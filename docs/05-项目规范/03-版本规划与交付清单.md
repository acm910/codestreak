# 版本规划与交付清单

## 1. 目的与适用范围

本文档规定 CodeStreak 的**版本策略、里程碑、范围边界、交付物、前置依赖、风险与发布检查**，作为排期承诺与验收依据。

- 适用范围：v1.0 及后续 v1.1/v1.2 的范围裁剪、里程碑验收、提审与回滚决策。
- 范围条目引用 [需求规格说明](../01-产品设计/02-需求规格说明.md) 的 `FR-xx` 与 [页面总览](../03-页面设计/01-页面总览与原型映射.md) 的 `P-01..P-04`，不在此重复定义需求内容。
- 排期以 **W1 = 2026-10-26** 为起点，一周 = W（周一至周日），不含缓冲期。

## 2. 版本策略

版本号采用语义化 `主.次.修订`（`versionName`），并映射单调递增的 `versionCode`：

| 位 | 递增条件 | 示例 |
| --- | --- | --- |
| 主版本 | 破坏性变更：数据结构迁移、bundleName 变更、一级导航重构 | `1.0.0` → `2.0.0` |
| 次版本 | 向下兼容的功能新增（新页面、新平台、新卡片） | `1.0.0` → `1.1.0` |
| 修订号 | 缺陷修复、文案与视觉微调，无接口与数据结构变化 | `1.0.0` → `1.0.1` |

| 版本 | 主题 | 定位 | 目标 |
| --- | --- | --- | --- |
| v1.0 | MVP 闭环 | 可用：4 页 + 4 平台同步 + 每日 2 题 + 连续天数与补签 | 上架并跑通"今日打卡 → 数据可见" |
| v1.1 | 增强 | 好用：题单详情、题目详情/题解、徽章墙、设置独立页、数据导出 | 提升留存与深度使用 |
| v1.2 | 社交与生态 | 可扩散：社区、Widget 卡片、平板适配、深浅色 | 拉新与桌面触达 |

`versionCode` 规则：`主*1000000 + 次*1000 + 修订`，如 `1.0.0 = 1000000`、`1.1.0 = 1001000`；只增不减，每次提审必须递增。

## 3. 里程碑

| 里程碑 | 名称 | 起止周 | 交付物 | 验收口径 | 负责人角色 |
| --- | --- | --- | --- | --- | --- |
| M0 | 设计定稿 | W1–W2 | 全部 31 份文档定稿、高保真四页、令牌代码骨架 | 文档 `status: 生效`、原型走查零阻塞问题、令牌与 `color.json` 逐项一致 | 产品经理 + 设计负责人 |
| M1 | 数据基座与同步 | W3–W5 | RDB 表与迁移、四平台同步适配器、难度归一化、连续天数与补签判定 | 四平台各 20 条样本归一化正确率 100%、同步成功率 ≥ 95%、断网可离线读库 | 技术负责人 |
| M2 | 四页闭环 | W6–W9 | P-01/P-02/P-03/P-04 四页可交互、弹层与全局状态、空/错/加载三态 | 四页主流程无阻断缺陷、数据全部来自真实同步、关键路径可回退 | 技术负责人 + 设计负责人 |
| M3 | 打磨与发布 | W10–W12 | 性能达标、安全与合规整改、上架物料、提审 | 第 10 节清单全绿、崩溃率 0、审核通过 | 项目管理组 + 产品经理 |

里程碑延期 > 3 个工作日必须触发第 12 节变更管理，并重排后续里程碑（不得压缩 M3 的测试窗口）。注意：本文件 **M0–M3 表示里程碑**，与 [需求规格说明](../01-产品设计/02-需求规格说明.md) 的模块编号 M1–M7（今日打卡 / 题单矩阵…）不同域，引用时须写明"里程碑 M1"或"模块 M2"。

> 里程碑的**周级排期、每阶段工作包与测试活动**见 [开发周期与测试计划](04-开发周期与测试计划.md)；该文把 M0–M3 展开为 W1–W12 的开发者/测试并行计划，并给出 G0–G3 门禁判据。

## 4. v1.0 范围

范围编号 `MUST-` / `SHOULD-` / `EXCL-` 为本文内部编号，不进入 [文档编写与命名规范](01-文档编写与命名规范.md) 的全局编号表；全局追溯仍以 `FR-xx` 为准。

### 4.1 必须做（不做则不可发布）

| 编号 | 范围项 | 对应页面 | 验收要点 |
| --- | --- | --- | --- |
| MUST-01 | 四平台账号绑定与当日数据同步 | P-01/P-04 | 4 平台全部可绑定；绑定失败的平台不阻塞其他平台 |
| MUST-02 | 每日 2 题达标判定与打卡 | P-01 | 达标即打卡成功；未达标展示差量与快捷入口 |
| MUST-03 | 连续天数计算与补签卡 | P-01/P-04 | 断签次日归零；补签卡消耗后连续天数回补且可追溯 |
| MUST-04 | 难度归一化 1–5 星与题单矩阵 | P-02 | 四平台映射表全覆盖；筛选/排序结果与库一致 |
| MUST-05 | 比赛日历（四平台赛事聚合） | P-03 | 按时间倒序、进行中高亮、可跳转报名页 |
| MUST-06 | 统计榜单（热力图 + 平台分布 + 完成率） | P-04 | 数据与库一致；空数据有占位说明 |
| MUST-07 | 本地持久化与备份恢复 | 全局 | 卸载重装可恢复；`EntryBackupAbility` 生效 |
| MUST-08 | 隐私政策与权限说明 | 全局 | 首启可查看、可撤回授权、无多余权限 |

### 4.2 应该做（有余量则做，缺失不阻塞发布）

| 编号 | 范围项 | 说明 |
| --- | --- | --- |
| SHOULD-01 | 手动"刷新同步"与上次同步时间展示 | 降低"数据不准"的客诉 |
| SHOULD-02 | 打卡庆祝动效与 Toast 反馈 | 复用 `C-16`/`C-18`，不新增视觉 |
| SHOULD-03 | 题单收藏与置顶 | 仅本地，无服务端 |
| SHOULD-04 | 统计页时间范围切换（7/30/90 天） | 复用同一查询 |
| SHOULD-05 | 同步失败的可读错误码提示 | 依赖 `ER-1xxx` 文案表 |

### 4.3 不做（明确排除，防止范围蔓延）

| 编号 | 排除项 | 理由 |
| --- | --- | --- |
| EXCL-01 | 用户注册/登录体系与云同步 | v1.0 纯本地，账号体系留到 v1.2 |
| EXCL-02 | 题目详情页与题解 | 依赖内容版权，排入 v1.1 |
| EXCL-03 | 社区、评论、排行榜社交互动 | 需审核与风控，排入 v1.2 |

| EXCL-05 | 平板与折叠屏适配 | v1.1 起支持，v1.0 仅 `phone` |

## 10. 发布前检查清单

**功能**

- [ ] 四页主流程（打卡、题单、比赛、统计）在真机各走通一遍。
- [ ] 四平台绑定、同步、解绑均可用，单平台失败不阻塞其他平台。
- [ ] 每日 2 题达标判定、连续天数、补签卡消耗与回补口径一致。
- [ ] 空态、加载态、错误态、断网态四态均有正确表现。
- [ ] 卸载重装与备份恢复后数据一致。

**性能**

- [ ] 冷启动到 P-01 首帧 ≤ 800ms（中端机），无白闪。
- [ ] 题单矩阵与榜单滚动帧率 ≥ 55fps。
- [ ] 单次同步耗时 ≤ 10s，超时有提示与重试。

**安全**

- [ ] token/Cookie 加密存储，日志无敏感信息。
- [ ] Web 组件域名白名单生效，外链不可跳出白名单。
- [ ] `code-linter` 零 error，`@security` 规则未 disable。

**合规**

- [ ] 隐私政策可查看、可撤回授权，权限声明与实际使用一致。
- [ ] 平台数据仅限本人，无批量抓取与再分发。
- [ ] 第三方字体与图标授权文件已归档。

**文案**

- [ ] 全量文案走查：无占位符、无英文残留、无错别字。
- [ ] 错误码文案均为用户可读中文，且与 `constants/ErrorCode.ets` 一致。

**多设备**

- [ ] 主流分辨率（1080×2340、1260×2720）无遮挡与截断。
- [ ] 系统字体放大 1.3 倍后关键信息不溢出。
- [ ] `compatibleSdkVersion 6.1.1(24)` 低版本设备安装可用。

**发布**

- [ ] `bundleName` 为 `com.codestreak.app`，`versionCode` 已递增。
- [ ] release 包为签名包，HAP ≤ 20MB、安装总包 ≤ 30MB。
- [ ] 上架物料（图标、截图、简介、更新说明）齐备。

## 11. 发布后 7 天观察与回滚

| 指标 | 观察口径 | 警戒阈值 | 处置 |
| --- | --- | --- | --- |
| 崩溃率 | 崩溃次数 / 启动次数 | > 0.5% | 立即定位，24h 内出补丁版本 |
| 同步成功率 | 成功同步平台数 / 尝试数 | < 90% | 关闭对应平台开关并回退适配器 |
| 打卡完成率 | 达标打卡用户 / 活跃用户 | < 40% | 复盘判定口径与入口可见性 |
| 次日留存 | D1 回访 / 首日新增 | < 25% | 排入 v1.1 优先级评估 |
| 启动耗时 P90 | 冷启动 | > 1.5s | 排查初始化与同步阻塞 |
| 负面反馈 | 应用市场 + 应用内反馈 | 同类问题 ≥ 5 条 | 归入 P0/P1 缺陷 |
| 数据异常 | 连续天数/补签卡错算反馈 | ≥ 1 例 | 触发数据核对与热修 |

回滚条件（满足任一即回滚到上一版本）：崩溃率 > 1%、同步成功率 < 70%、出现数据丢失或错算、审核方要求下架整改。回滚后 48h 内出根因分析与修复计划。

## 12. 变更管理

需求或范围变更须填写影响评估，经项目管理组确认后方可进入迭代：

| 评估项 | 判定 | 处置 |
| --- | --- | --- |
| 是否在 v1.0 必须做范围内 | 是 / 否 | 否 → 排入 v1.1 待评池 |
| 是否影响已冻结的数据模型 | 是 / 否 | 是 → 需 DBA 级评审 + 迁移方案 |
| 是否影响里程碑排期 | 是 / 否 | 是 → 重排后续里程碑并同步全员 |
| 是否影响已生效文档 | 是 / 否 | 是 → 同 PR 修订文档并升版本（见 05-01） |
| 是否影响已提审/已上架版本 | 是 / 否 | 是 → 走热修流程，不夹带新功能 |
| 审批人 | 角色 | 范围 → 产品经理；排期 → 项目管理组；技术 → 技术负责人 |

变更冻结窗口：提审前 5 个工作日（W11 起）仅接受 P0 缺陷修复。
