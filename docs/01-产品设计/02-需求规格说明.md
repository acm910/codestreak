## 2. 需求编号规则与优先级

### 2.1 编号规则

| 前缀 | 含义 | 格式 | 示例 |
| --- | --- | --- | --- |
| `FR-` | 功能需求，全局连续编号 | `FR-` + 两位序号 | `FR-01` |
| `NFR-` | 非功能需求 | `NFR-` + 两位序号 | `NFR-05` |
| `M1`–`M7` | 需求模块 | `M` + 序号 | `M3 比赛日历` |
| `R-` | 风险/假设（见 01-01 第 10 节） | `R-` + 序号 | `R-2` |
| `PA-` | 优先级判定记录（仅评审用，不入库） | — | — |

编号一经发布不复用：删除的需求把编号置为"作废"，不回收给新需求。

### 2.2 优先级定义

| 优先级 | MoSCoW | 判定标准 | 发布影响 |
| --- | --- | --- | --- |
| P0 | Must have | 缺失则核心链路（打卡 / 连胜 / 比赛 / 统计）不成立 | **阻断发布**，必须 100% 通过 |
| P1 | Should have | 影响体验完整性，有明确降级方案 | 可延至 v1.0.x，但需产品书面确认 |
| P2 | Could have | 锦上添花，可不实现 | 允许以占位或提示替代 |
| — | Won't have（本次） | 与 v1 定位冲突或成本过高 | 见第 7 节 |

### 2.3 验收标准写法

1. 行为类需求统一用 **Given / When / Then**；每个 FR 至少 1 条主路径。
2. 视觉与文案一致性用 **checklist**（如"按钮文案为『完成打卡』且禁用后为『已打卡 AC』"）。
3. 所有验收标准必须可在真机复现，不含"美观""流畅"等不可判定词；性能类转入 NFR。

### 4.8 关键状态机

每日打卡状态（`daily_status`）与补题状态（`upsolve_status`）是两条独立状态机，不得互相驱动。

```text
[每日打卡]
00:00 生成目标
    │
    ▼
 pending ──target_progress≥2──▶ achieved ──(次日 00:00 归档)──▶ 计入 total_checkin_days
    │                  │
    │ 23:59 未达标       └─▶ current_streak +1，触发 C-16
    ▼
 missed ──(7 日内消耗补签卡)──▶ makeup ──▶ current_streak 重算并 +1
    │
    └──(超 7 日)──▶ missed（终态，不再可补）

[赛后补题]
比赛结束
    │
    ├─ 赛中 AC ──▶ ac_in_contest（不计入补题率分子）
    ├─ 未过 ──▶ pending ──标记──▶ ac_after（计入分子）
    │              └─放弃──▶ skipped（计入分母，不计入分子）
    └─ 未参赛 ──▶ 不生成补题任务
```

规则要点：

1. `missed` 只有在 7 天内且余额 >0 时可转 `makeup`，其余情况为终态。
2. `upsolve_rate` 的分子只含 `ac_after`，`ac_in_contest` 不计入，避免"赛中全过也算补题"的虚高。
3. 状态流转一律写事件日志（含时间戳与来源：手动/同步/补签），供统计回溯。
