# 产品概述与定位

## 1. 目的与范围

本文定义 CodeStreak 的产品定位、目标用户、价值主张、边界与成败判据，是需求规格（01-02）、信息架构（01-03）、术语与数据字典（01-04）的上位依据。

| 项 | 说明 |
| --- | --- |
| 适用读者 | 产品、交互/视觉设计、HarmonyOS 客户端开发、测试、运营 |
| 覆盖版本 | v1.0，HarmonyOS 单 entry 模块（ArkTS + ArkUI 声明式） |
| 不覆盖 | 交互细节与验收标准（01-02）、页面结构与用户旅程（01-03）、字段与枚举取值（01-04） |
| 冲突裁决 | 定位类结论以本文为准；颜色/令牌一律以 [设计令牌规范](../02-设计规范/02-设计令牌规范.md)（02-02）为准 |
| 事实基线 | 代码现状仅为 Entry 模板，本文件所述功能均为**待实现**，不得被当作既有能力引用 |

## 2. 一句话定义

> **CodeStreak 把分散在 LeetCode、Codeforces、洛谷、AtCoder 上的刷题行为，收敛为"每天 2 题、断签可补、赛后可追"的一条不可断连胜记录；面向算法竞赛选手与求职面试者，用一块暗色终端面板同时承载打卡、选题、参赛与复盘。**

三个支撑点：

1. **是什么**：跨平台刷题"连续打卡 + 赛训一体化"工具，国产 HarmonyOS 原生客户端，暗色终端风，品牌眉标 `CODESTREAK // CLI`。
2. **给谁**：需要高频、可量化、可坚持的训练节奏的人——秋招应届生、现役竞赛选手、自驱型 CS 学生。
3. **凭什么**：每日 2 题刚性目标 + 四平台统一难度 `difficulty_norm` + 赛后补题闭环 + 补签卡保全机制，四者组合在现有工具中无人同时提供。

## 3. 问题背景

| 编号 | 问题 | 现象 | 用户代价 |
| --- | --- | --- | --- |
| PB-1 | 刷题坚持难 | 计划"每天 3 题"，第 4 天因加班断掉，此后放弃 | 训练量归零，简历项目无法量化 |
| PB-2 | 跨平台数据割裂 | AC 分布在大厂/洛谷/CF 四个账号，进度靠 Excel 手记 | 无法判断短板，重复刷已会题 |
| PB-3 | 赛训脱节 | 打完比赛只记"打了"，赛后 48 小时内不补题，能力不增长 | 比赛变成娱乐，Rating 长期停滞 |

### 3.1 刷题坚持难（PB-1）

| 维度 | 现状 |
| --- | --- |
| 现象 | 目标靠自定且无反馈，单日中断无补救，连续性一旦破坏即整体放弃 |
| 用户代价 | 训练曲线呈"三分钟热度"锯齿，月度有效训练天数普遍低于 8 天 |
| 现有方案缺口 | 平台自带打卡仅统计"提交"，不区分"是否达标"；习惯类 App 无法识别题目难度与平台 |

### 3.2 跨平台数据割裂（PB-2）

| 维度 | 现状 |
| --- | --- |
| 现象 | LeetCode 求职高频、CF/洛谷/AtCoder 竞赛题各有难度体系（Easy-Medium-Hard / Rating / 入门-省选 / A-F） |
| 用户代价 | 无法横向比较"我今天做的题到底有多难"，题单无法跨平台拼装 |
| 现有方案缺口 | 无工具提供跨平台统一难度刻度（本项目归一化为 1–5 星 `difficulty_norm`） |

### 3.3 赛训脱节（PB-3）

| 维度 | 现状 |
| --- | --- |
| 现象 | 赛程分散在四个官网，报名/开赛提醒靠记忆；赛后题目不做归档 |
| 用户代价 | 错过比赛；赛中未过的题赛后不再回看，同类题反复失手 |
| 现有方案缺口 | 平台不提供"赛后待补题清单"，日历类工具不识别题目与通过状态 |

## 4. 目标用户与画像

三条画像共享同一判定：**只要"每天必须做够 2 题"这件事对他是刚需，就是目标用户**；反之只把刷题当兴趣消遣者不在服务范围。

### 4.1 画像 A · 面试冲刺的应届生

| 维度 | 内容 |
| --- | --- |
| 典型身份 | 大三下至应届，目标互联网/外企后端、算法岗，秋招前 3 个月 |
| 目标 | 8 周内覆盖高频 300 题，形成可讲的项目化训练记录 |
| 痛点 | 不知道"该刷哪些题"；刷完记不住；面试前无法证明训练量 |
| 关键场景 | 21:30 通勤后回宿舍，打开 App 看今日 2 题，跳 LeetCode 做完回端打卡 |
| 成功标准 | 连续 ≥ 30 天、题单"代码随想录核心 60 题"完成度 ≥ 80%、能导出训练记录 |
| 使用频次 | 每日 1–2 次，单次 20–45 分钟 |

### 4.2 画像 B · 现役竞赛选手

| 维度 | 内容 |
| --- | --- |
| 典型身份 | 大二至研一，CF 1400–1900 / 洛谷提高组，参加 ICPC、CCPC、ABC、Div.3 |
| 目标 | 稳定上分，赛后 48 小时内补完未过题，训练数据可复盘 |
| 痛点 | 赛程靠群消息；补题靠记忆；缺乏"补题完成率"这类过程指标 |
| 关键场景 | 周六 19:30 收到 ABC 提醒，赛后 22:00 在 P-03 补题专区逐题标记 |
| 成功标准 | 当月补题率 ≥ 80%、比赛提醒 100% 到场、连胜不因比赛日中断 |
| 使用频次 | 每日 1 次 + 比赛日 3–4 次 |

### 4.3 画像 C · 自驱型 CS 学生

| 维度 | 内容 |
| --- | --- |
| 典型身份 | 大一至大三，无明确求职时间表，以"变强"为动机，喜好看数据 |
| 目标 | 建立可持续的算法训练习惯，观察难度分布是否向 ★4/★5 迁移 |
| 痛点 | 缺乏正反馈；断签后无补救手段，直接放弃整段计划 |
| 关键场景 | 周日晚上进 P-04 看热力图与难度分布，决定下周主攻方向 |
| 成功标准 | 连续天数中位数 ≥ 7、累计打卡 ≥ 100 天、至少解锁 3 枚徽章 |
| 使用频次 | 每日 1 次，周末 1 次长会话（5–15 分钟） |

## 5. 价值主张与差异化

### 5.1 主张拆解

| 支柱 | 对用户的承诺 | 可验证表现 |
| --- | --- | --- |
| 刚性节奏 | 每天只有 2 题，1 道今日核心推荐 + 1 道竞赛挑战二选一，做完即可收工 | P-01 状态胶囊由"待完成 1/2"变为"今日已拉满 2/2"，C-16 弹层确认连胜 +1 |
| 跨平台归一 | 四平台题目统一到 1–5 星 `difficulty_norm`，题单可混装 | 题单矩阵库支持按归一难度排序与 ★1–★5 筛选 |
| 赛训闭环 | 比赛不仅是日程，还产出赛后待补题清单与补题完成率 | C-26 倒计时 + C-27 补题率（示例 75%，目标 80%） |
| 断签可救 | 补签卡余额 2 张，把"断了就放弃"变成"补一天继续" | C-38 展示余额与获取规则 |

### 5.2 与同类产品对比

| 能力 | CodeStreak | LeetCode 中国站 | 洛谷 | Codeforces | 通用打卡/习惯 App |
| --- | --- | --- | --- | --- | --- |
| 核心定位 | 跨平台连胜 + 赛训一体 | 单平台题库与竞赛 | 单平台题库与竞赛 | 单平台竞赛 | 任意习惯打卡 |
| 跨平台聚合 | **四平台**统一视图 | 仅 LC | 仅洛谷 | 仅 CF | 无题目语义 |
| 连续打卡/断签补救 | 达标制 + 补签卡 | 提交日历，无达标制 | 无 | 无 | 有连续天数，无题目语义 |
| 难度归一化 | **1–5 星 + 0.5 星粒度** | Easy/Medium/Hard | 入门–省选 7 档 | Rating | 无 |
| 赛事聚合日历 | **四平台 + ICPC/CCPC** | 仅周赛 | 仅月赛 | 仅 CF | 无 |
| 赛后补题闭环 | **待补题清单 + 补题率** | 无 | 无 | 无 | 无 |
| 在线判题/代码运行 | 不做（外跳） | 有 | 有 | 有 | 无 |
| 数据归属 | 本地优先，可导出 | 平台私有 | 平台私有 | 平台私有 | 弱 |

结论：与三个平台不是替代关系而是**聚合层**；与习惯类 App 的差异在于"打卡对象是带难度、带平台、带比赛语义的题目"，因此不可能由通用工具覆盖。

## 6. 产品边界与非目标

### 6.1 v1.0 范围内

1. 四个 Tab：今日打卡（P-01）、题单矩阵（P-02）、比赛日历（P-03）、统计榜单（P-04）。
2. 每日 2 题目标：P-01 两张目标卡各计 1 题，`daily_target_progress` 达 2 判达标；当日全部 AC 数（`daily_ac_count`）另计，用于热力图与"今天已打卡 N 题"。
3. 补签卡消耗与补签（余额 2 张，仅消耗不售卖）。
4. 四平台账号绑定与数据同步：Codeforces、AtCoder 走自动同步（公开只读接口）；LeetCode 中国站、洛谷走授权同步（内置 WebView 登录后只读本人记录）；任一平台失效即降级为手动打卡，界面始终标注同步方式与时间（三模式定义见 [平台同步与难度归一化](../04-技术设计/04-平台同步与难度归一化.md)）。
5. 比赛日历聚合、单场倒计时、赛前提醒、赛后补题清单。
6. 暗色单主题，`compatibleSdkVersion 6.1.1(24)`、`targetSdkVersion 26.0.0`，单 entry 模块；`bundleName` 由 `com.example.project` 改为 `com.codestreak.app`（须同步改 `AppScope/app.json5` 与签名配置）。

### 6.2 明确非目标

| 非目标 | 原因 | v1 替代路径 | 后续版本 |
| --- | --- | --- | --- |
| 在线判题 / 代码运行 | 需沙箱、语言运行时与评测机，成本远超产品价值 | 深链跳转平台做题，回端确认 AC | 不做 |
| 托管题目内容 | 版权与内容维护风险 | 仅存题号、标题、难度、标签等元数据 | 不做 |
| 社区论坛 / 评论 | 需要审核与运营投入，非连胜闭环必需 | 无 | 不做 |
| 支付 / 订阅 | 商业化未验证 | PRO 徽标仅展示，点击说明"暂未开放" | 待定 |
| 好友体系与实时对战 | 依赖社交关系链，冷启动无内容 | 榜单使用预置样例数据 | v1.1 |
| 浅色主题 | 与暗色终端风定位冲突 | 强制 `COLOR_MODE_DARK` | 不做 |
| 沉浸时长精确统计 | 不做判题则无服务端可信数据源 | `focus_minutes` 定义为外跳往返估算值 | 待定 |

## 7. 北极星指标与指标树

### 7.1 指标树

```text
北极星：WSD / WAU（周人均打卡达标天数）
├─ A 激活 Activation
│  ├─ A1 新装 → 24h 内绑定 ≥1 平台账号（目标 ≥60%）
│  ├─ A2 新装 → D0 完成 2 题（目标 ≥55%）
│  └─ A3 人均绑定平台数（目标 ≥2.0）
├─ B 留存 Retention
│  ├─ B1 D1 / D7 / D30 留存（D7 ≥35%）
│  ├─ B2 周达标 ≥4 天用户占比（目标 ≥45%）
│  └─ B3 连续天数中位数（目标 ≥7 天）
├─ C 深度 Depth
│  ├─ C1 赛后补题率（目标 ≥50%，示例口径 15/20=75%）
│  ├─ C2 竞赛挑战二选一参与率（目标 ≥40%）
│  └─ C3 题单完成度周增量（目标 ≥3 题/人/周）
└─ D 健康度 Health
   ├─ D1 补签卡使用率（≤8%，过高说明目标过载）
   ├─ D2 同步成功率（CF API ≥99%）
   └─ D3 崩溃率 <0.3% / 冷启动 <800ms
```

### 7.2 指标定义

| 指标 | 公式 | 统计口径 | 数据来源 | v1.0 目标 |
| --- | --- | --- | --- | --- |
| WSD/WAU（北极星） | Σ 当周 `daily_status = achieved` 天数 ÷ 周活跃用户数 | 自然周（周一 00:00–周日 24:00，Asia/Shanghai）；活跃 = 当周有任意会话 | 客户端埋点 | ≥ 4.0 天 |
| D7 留存 | 第 7 日有会话的新用户 ÷ 新用户 | 按首次启动日 cohort | 埋点 | ≥ 35% |
| 绑定转化率 | 24h 内绑定 ≥1 平台的用户 ÷ 新用户 | `bind_status = bound` 且校验通过 | 客户端 + 平台接口 | ≥ 60% |
| 首日达标率 | D0 完成 2 题的用户 ÷ 新用户 | 含手动打卡 | 埋点 | ≥ 55% |
| 赛后补题率 | 当月 `ac_after` ÷（`ac_after` + `pending` + `skipped`） | 自然月，仅计已结束且标记参赛的比赛 | 派生字段 `upsolve_rate` | ≥ 50% |
| 连续天数中位数 | 活跃用户 `current_streak` 中位数 | 月末快照 | 派生 | ≥ 7 天 |
| 补签卡使用率 | 当月补签达标天数 ÷ 当月达标天数 | 反映目标是否过载 | 派生 | ≤ 8% |

## 10. 关键风险与假设

| 编号 | 类型 | 描述 | 应对 |
| --- | --- | --- | --- |
| R-1 | 假设 | 用户愿意在平台完成题后回端手动确认 AC | 提供一键"完成打卡"+ 赛后批量标记，单次操作 ≤2 次点击 |
| R-2 | 风险 | LeetCode 中国站与洛谷无官方开放 API，需登录态；AtCoder 依赖第三方公开 API | 采用授权同步（WebView 登录后只读本人记录）+ 手动兜底；界面标注同步方式，见 04-04 |
| R-3 | 风险 | 平台接口频率限制、反爬或登录态失效导致同步失败 | 只读本人数据、频率 ≤1 次/2 分钟/用户、Cookie 加密存储、失败自动降级手动并提示重新授权 |
| R-4 | 风险 | 每日 2 题目标对在职用户过载，导致补签卡滥用 | 补签卡使用率作为健康度指标监控 |
| R-5 | 假设 | 暗色单主题在强光环境下可接受（本产品主场景为夜间/工位） | 提供字号放大无障碍设置 |
