# 通过条件与缺陷管理

## 1. 目的与范围

本文定义三件事：**什么算通过**（可量化、可判定、无歧义）、**缺陷怎么定级与流转**、**例外怎么批**。它是 G0–G3 门禁的判定依据，也是测试报告与发布签署的输入。

- 通过条件分四层：用例级 → 模块级 → 阶段级 → 发布级，下层不通过则上层不成立。
- 所有阈值均可由测试报告中的数据直接计算，不接受"基本可用""大致通过"这类结论。

## 4. 指标定义

| 指标 | 公式 | 达标线 |
| --- | --- | --- |
| 用例通过率 | 通过数 ÷ 执行数（按优先级分别统计） | P0 = 100%；P1 ≥95% |
| 自动化覆盖率 | 自动化用例数 ÷ 总用例数 | ≥50%（当前 56/111） |
| 单测覆盖率 | 被覆盖行数 ÷ 可执行行数（domain 层） | ≥80%（关键模块 ≥90%） |
| 缺陷密度 | 缺陷数 ÷ 千行代码（KLOC） | 参考值 ≤15；不设硬门禁 |
| 缺陷修复率 | 已关闭数 ÷ 发现数 | ≥95% |
| 平均修复时长 MTTR | Σ(关闭时间 − 创建时间) ÷ 关闭数 | P0 ≤24h；P1 ≤3 工作日 |
| 逃逸缺陷率 | 上线后发现的缺陷 ÷ 上线前发现总数 | ≤5% |
| crash-free 用户率 | 无崩溃用户 ÷ 活跃用户 | ≥99.5% |
| 同步成功率 | 成功任务 ÷ 总任务 | ≥95% |
| 需求覆盖率 | 有对应用例的 FR 数 ÷ FR 总数 | 100% |

## 5. 缺陷管理

### 5.1 等级定义

| 等级 | 定义 | 典型例子 | 响应/修复 | 发布要求 |
| --- | --- | --- | --- | --- |
| **P0 阻断** | 崩溃、数据丢失/损坏、主流程不可用、隐私泄露、资金/账号风险 | 打卡后数据丢失；Cookie 明文落库；启动即崩溃；同步导致库损坏 | 4h 响应 / 24h 修复 | 必须清零（不可豁免） |
| **P1 严重** | 核心功能错误、口径错误、明显错误文案 | 连续天数算错；难度映射错档；打卡按钮无效；占比合计 99.9% | 当迭代修复 | 必须清零 |
| **P2 一般** | 非核心功能异常、体验问题、边界缺陷 | 筛选组合偶发空结果；骨架闪烁；次要文案错字 | 下迭代 | ≤10（发布时 ≤5） |
| **P3 轻微** | 视觉细节、极端场景、优化建议 | 图标 1vp 偏差；极长标题截断方式 | 排期 | 可遗留 |

判定原则：**按影响而非按来源**。同一现象在低端机才出现但导致崩溃，仍为 P0。

### 5.2 状态流转

```text
新建 ──确认──▶ 已确认 ──分派──▶ 修复中 ──▶ 待验证 ──▶ 已关闭
  │              │                │            │
  ├─重复/无效──▶ 已驳回            └─延期(P2/P3)─▶ 已排期
  └─信息不足──▶ 待补充 ──补充后──▶ 已确认
```

规则：

1. **确认权在测试**：开发不得自行关闭；驳回须给出依据（复现失败/需求如此）。
2. **回归由他人执行**：修复者不得验证自己的修复。
3. **重开**：验证失败直接重开并升级一级（P2→P1），累计两次重开由项目负责人介入。
4. **延期**：仅 P2/P3 可延期，须写明目标版本并在发布报告中列出。

### 5.3 缺陷必填字段

`ID / 标题 / 等级 / 模块 / 环境（设备+版本）/ 前置条件 / 复现步骤 / 实际结果 / 预期结果 / 复现率 / 附件（日志、截图、DB 片段）/ 关联用例 / 责任人 / 状态`

复现率 <100% 的缺陷必须附"最后一次失败日志"，否则测试可拒绝受理。

## 6. 收敛与停止准则

### 6.1 缺陷收敛

| 条件 | 要求 |
| --- | --- |
| 新增趋势 | 连续 3 个工作日新增 P0/P1 = 0 |
| 修复趋势 | 累计修复率 ≥95%，未修复项均已成文豁免或排期 |
| 重开率 | 重开缺陷 ÷ 已关闭 ≤5% |
| 回归通过 | 上轮全部缺陷回归 100% 通过 |

### 6.2 停止测试准则（全部满足才可停止）

1. 计划内用例执行率 **100%**（含手工与自动化）；
2. P0 通过率 100%，P1 ≥95%；
3. 缺陷收敛条件满足；
4. 性能、安全、兼容、稳定性四项专项报告已出且达标；
5. 无未决的 P0/P1，P2 数量在阈值内；
6. 需求追踪矩阵无空白（每个 FR 至少 1 条用例）。

任一不满足则延长测试，不得以"时间到了"为由发布。

## 7. 豁免与例外

### 7.1 不可豁免项（红线）

- 数据丢失或损坏；
- 凭据/隐私泄露；
- 崩溃导致不可用；
- 违反平台 ToS 或隐私法规；
- 审核明确驳回项。

上述任一存在即**阻断发布**，不接受豁免。

### 7.2 可豁免项与流程

| 项 | 可豁免条件 | 审批人 | 最长有效期 |
| --- | --- | --- | --- |
| P2 缺陷 | 有明确规避方式且不影响主流程 | 项目负责人 | 1 个版本 |
| 性能轻微超标（≤10%） | 低端机限定场景 | 项目负责人 + 技术 | 1 个版本 |
| 兼容性单机型问题 | 该机型占比 <1% 且有降级 | 项目负责人 | 1 个版本 |
| UI 像素级偏差 | 不影响识别与操作 | 设计负责人 | 永久（记录） |
| 文案优化建议 | 非错误文案 | 产品 | 永久（记录） |

豁免记录字段：`编号 / 项 / 原因 / 影响评估 / 规避方式 / 审批人 / 批准日期 / 失效版本 / 跟踪人`，并写入发布报告附录。

### 8.2 阶段测试报告（G1/G2/提审）

| 章节 | 必填内容 |
| --- | --- |
| 1 概述 | 测试范围、版本、环境、起止时间 |
| 2 执行统计 | 按模块 × 优先级 × 结果的矩阵 |

| 5 需求覆盖 | FR 追踪结果，未覆盖项说明 |
| 6 风险与遗留 | 未修复缺陷、豁免项、已知限制 |
| 7 结论 | **通过 / 有条件通过 / 不通过**（必须三选一） |
